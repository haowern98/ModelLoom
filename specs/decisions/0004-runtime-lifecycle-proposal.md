## 3. Accepted phased D01 exception

The earlier rule required full audit completion/review before exact hosting selection. The user now accepts this documented mapping and the existing Windows evidence as the prerequisite **for the initial Windows development slice only**:

- Use supported Electron and upstream engine interfaces. Exact proprietary GUI/core framing and internal implementation are not prerequisites to reproduce the approved observable contract; differences remain recorded.
- Stop trying to prove Bionic's ordinary native-crash transcript policy before coding ModelLoom. Test ordinary native abort, GUI survival, partial-output retention and recovery against ModelLoom before claiming J13 acceptance.
- Defer macOS/Linux reference and implementation evidence to those platform milestones. Do not claim support or cross-platform acceptance from Windows results.
- Keep update trust, actual package activation, per-request context/resource correctness, durable storage and distributed security as blockers for their affected tasks. This exception does not waive S15-S17, D03/D04/D09/D11/D12 or release gates.

D01 stays open overall, with this narrow development permission recorded separately. The affected AGENTS.md gate, audit plan, decision register, technical/integration specifications and code-quality guidance are reconciled with this accepted ADR. Live activation, production update security, ordinary native-crash acceptance and other platform/release evidence keep their stated gates.

## 4. Ownership, authentication and lifecycle contract

For Windows, recommend a small C++ Node-API process-control adapter using deployment-scoped Job Objects. The desktop host holds a non-inherited lifetime handle for its core/engine containment, with a separate nested engine job so engine unload/forced recovery can leave the utility core alive. The independent headless host holds its own engine containment. Disable breakaway. Admit the utility core to containment before granting launch capability; create native children suspended, assign containment, then resume. Reject containment failure before loading a model. Keep trusted handles and creation/session identity; PID/name/port alone never authorizes termination. On lost core communication, the desktop broker closes admission and tears down its owned engine within the same shutdown policy; it does not attach to another deployment.

Windows documents associated-child containment and kill-on-last-job-handle-close. Those mechanisms support this proposal but require packaged tests of nesting, startup races, parent exit and unrelated deployment survival. Job membership is not a security sandbox. [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). macOS/Linux need adapters with the same ownership contract and independently demonstrated cleanup; a process group alone is not assumed sufficient for abnormal-owner-exit cleanup.

Define states `stopped -> starting -> loading -> ready -> stopping -> stopped`, with `failed` reachable from startup or active operation. Each operation carries deployment, package, model-session and request identity. Reject stale-session commands/events. Launch arguments are an allowlisted argument vector with no shell; package/model paths must be resolved from approved assets and checked for escape/reparse behavior.

Give each engine a fresh private credential, supplied through a restricted ephemeral key file where supported, never through renderer state, logs or visible command arguments. Delete it after confirmed engine exit; fail closed if permissions cannot be established. Allow only selected routes/methods through the adapter. Health alone cannot authenticate activation: match the owned listener/process and authenticated model/build response to the selected package/session before reporting ready. This does not protect against a compromised same-user account.

The inspected [upstream source snapshot](https://github.com/ggml-org/llama.cpp/tree/4f31296a907d73f3409f720429bcf31111615d77) is a candidate validation pin, not yet a distributable build. Its [server documentation](https://github.com/ggml-org/llama.cpp/blob/4f31296a907d73f3409f720429bcf31111615d77/tools/server/README.md) documents key-file authentication, public health, streaming and parallel slots. Build identity, dependency hashes, backend/driver compatibility and graceful shutdown signaling must be proven for the selected build; no guessed shutdown route is part of this proposal.

Accepted initial development limits: 180 seconds for model startup; 5 seconds for graceful teardown followed by 2 seconds for forced-exit confirmation; 1 MiB per control message. These are development policy values, not discovered LM Studio defaults. Timeout cancels the operation and cleans up owned resources; a cleanup failure reports failure rather than success. Do not enable a real runtime adapter until its graceful-stop method is demonstrated within this policy.

The accepted later local-generation development policy is four active predictions and eight pending requests, FIFO admission, immediate `QUEUE_FULL` rejection beyond that bound and caller-owned cancellation. These are development choices, not a measured reference queue limit or release capacity; D09's resource/correctness validation remains open. Keep one core-owned pending queue; submit only admitted work to native slots. Preserve configured per-request context and sampling; if the chosen concurrency cannot fit, reject preflight and request an explicit settings choice rather than silently reduce context, quantization or concurrency. Concurrency, native cancellation and numerical behavior still need real-engine evidence. The first fixture-backed lifecycle plan does not implement the scheduler.

## 5. Package verification boundary

For initial core/process development, use test fixtures rather than launching an unverified installed runtime. The engine adapter accepts only a verified-package capability issued by the verifier; a pathname or caller-provided hash is insufficient. Fixture capabilities are confined to the test harness and cannot activate production binaries.

Before real Bonsai loading, accept and implement a minimal signed bootstrap package contract: trusted root source, signed metadata linking the exact build/platform/backend and every executable dependency, bounded extraction/path checks, compatible core protocol, launch-time integrity checks and a verified installation receipt. Prefer an existing TUF client; test keys remain fixtures and private signing keys never ship to users. Root/release-key custody, expiry/offline/revocation handling and recovery require an explicit D11 security design before live activation or distribution. This is the named remaining security blocker, not another generic audit request. [TUF specification](https://theupdateframework.github.io/specification/latest/).

Later updates stage into a new version directory, never overwrite executing files, activate only between sessions and retain a verified prior version. Recovery/rollback is explicit initially. Failed activation leaves the session unavailable and offers the prior verified version; it never silently loads another model or accepts older trusted metadata.

## 6. First coding scope and acceptance

**First implementation task after plan approval and scoped PROCEED:** shared lifecycle contracts and state machine, fake process/engine adapters, and failure/shutdown tests. This needs no real model, network listener, signing keys, native build or UI modification. Follow with the process-control adapter and desktop/headless hosts, exercised with harmless owned child fixtures.

Tests must cover exit during loading/generation, stale replies, exactly one terminal outcome, partial-record preservation, bounded shutdown, failed containment, PID reuse, port collision, owner crash and two independent deployments where one quits without killing the other. A native abort fixture tests an actual abnormal native exit separately from a forced kill. Persistence and live-GUI journeys are later acceptance tasks, not passed by fixture records.

**Next local inference task:** verified upstream package, same selected GGUF/configuration, truthful readiness, streamed reply, cancellation, explicit reload and owned exit. Its blockers are the bootstrap verification contract, exact build/host pins, resource/context preflight and proven graceful stop. ModelLoom's own evidence closes those tests; another full Bionic audit is not required under the proposed exception.

Do not change renderer layouts/styles, enable existing preview controls, add public API exposure, implement networking/workers, create durable history, add a downloader, or attempt speculative decoding in the first task. Future bindings reuse the existing UI under their own approved functional scope. Headless shares core behavior; it does not get a second engine manager.
