# Architecture and product decisions

**Updated:** 2026-10-06. This register records decision status; it does not grant implementation permission.

## Recorded baseline

[ADR-0001: product and UI baseline](0001-product-and-ui-baseline.md) records the initial agreed requirements. [ADR-0002: LM Studio runtime direction](0002-lm-studio-runtime-direction.md) records the later accepted reference/audit direction, grouped llama-server naming, crash isolation, independent upgrades, shared headless machinery, and shutdown ownership. ADR-0002 supersedes ADR-0001's earlier process-name prohibition. [ADR-0004](0004-runtime-lifecycle-proposal.md), accepted on 2026-10-06, records the shared TypeScript core, desktop utility/headless hosts, separate native engine, deployment ownership and initial Windows development exception. Implementation still needs its reviewed plan and scoped authorization; D01 remains open overall.

### Renderer UI baseline reconciliation, 2026-10-05

The user fixed the current UI and requested documentation reconciliation without further UI changes. [UI-SPEC](../UI-SPEC.md#current-ui-baseline-2026-10-05) records the current shell, Models/configuration, Cluster, Chat and API, their sizing/placement and the unavailable integrations. Home opens Chat; API is directly after Models; More contains Chat only. Settings remains a placeholder. Explore and the proposed Models tabs/two-column layout are deferred; the existing compass, identifier and GGUF pills remain.

D08 is partially settled for these current layouts/navigation and supported demo-window reflow. It remains open for attachments, deferred destinations/Settings, assets/themes and release/platform accessibility evidence. D10's desktop TypeScript/React/pnpm/Vite/Forge/testing choices are approved and implemented; core TypeScript and the initial hosting direction are now accepted under ADR-0004; native tool/build pins, platform floors and release validation remain open. No runtime/network/security/correctness decision is closed by UI implementation or documentation reconciliation.

## Recording a decision

The [six-area readiness investigation](../../docs/research/IMPLEMENTATION-READINESS-INVESTIGATION.md) adds current source evidence and proposed contracts for D01/D03/D04/D09/D11/D12. In particular, engine-owned deferred work, stock tensor-cache integrity/quota gaps, headless secret storage, protocol-versus-build compatibility, and batching/numerical exactness require explicit treatment. Research completion does not substitute for design acceptance or actual boundary validation.

The [first-release decision proposals](../../plans/DECISION-PROPOSALS.md) offer concrete stack, storage, API, UI, and verification defaults for review. The [testing specification](../TESTING-SPEC.md) is a draft acceptance/evidence contract. The [partial passive Windows inventory](../../docs/research/LM-STUDIO-PASSIVE-AUDIT.md) supplies actual package metadata for D01, but leaves running hosting/lifecycle and Linux/macOS evidence unresolved. None of these documents automatically accepts or closes a decision above.

Create a numbered Markdown ADR when an actual choice is reviewed: title, date, status, requirement links, context, options, chosen approach, consequences, security impact, validation evidence, and superseded decisions. Use statuses Proposed, Accepted, Rejected, or Superseded. Keep previous records when a decision changes. Update this register and the affected specs; do not silently treat a proposal as accepted.

Specs contain the behavior and constraints; ADRs explain why an approach was chosen. Plans record the sequence and execution evidence. No network/security/signing architecture decision has been accepted merely by creating this register.
