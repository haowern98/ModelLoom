## Recording a decision

The [six-area readiness investigation](../../docs/research/IMPLEMENTATION-READINESS-INVESTIGATION.md) adds current source evidence and proposed contracts for D01/D03/D04/D09/D11/D12. In particular, engine-owned deferred work, stock tensor-cache integrity/quota gaps, headless secret storage, protocol-versus-build compatibility, and batching/numerical exactness require explicit treatment. Research completion does not substitute for design acceptance or actual boundary validation.

The [first-release decision proposals](../../plans/DECISION-PROPOSALS.md) offer concrete stack, storage, API, UI, and verification defaults for review. The [testing specification](../TESTING-SPEC.md) is a draft acceptance/evidence contract. The [partial passive Windows inventory](../../docs/research/LM-STUDIO-PASSIVE-AUDIT.md) supplies actual package metadata for D01, but leaves running hosting/lifecycle and Linux/macOS evidence unresolved. None of these documents automatically accepts or closes a decision above.

Create a numbered Markdown ADR when an actual choice is reviewed: title, date, status, requirement links, context, options, chosen approach, consequences, security impact, validation evidence, and superseded decisions. Use statuses Proposed, Accepted, Rejected, or Superseded. Keep previous records when a decision changes. Update this register and the affected specs; do not silently treat a proposal as accepted.

Specs contain the behavior and constraints; ADRs explain why an approach was chosen. Plans record the sequence and execution evidence. No network/security/signing architecture decision has been accepted merely by creating this register.
