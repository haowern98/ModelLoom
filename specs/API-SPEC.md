# ModelLoom local API specification

**Date:** 2026-10-13; initial proposal prepared 2026-10-10

**Status:** Initial Windows development contract implemented under accepted ADR-0006. Production/platform acceptance, real-model equivalence and independent security review remain open.

**Reference:** Observed Bionic 1.1.7+7 behaviour and dated official LM Studio documentation, constrained by ModelLoom's accepted product, security and inference requirements. ChatGPT is the UI reference across the whole app; apple-design guides interaction and polish.

## 1. Purpose and authorization

Other applications should be able to use ModelLoom much as they use LM Studio: start a server in the app, copy its address, authenticate, select the served model identifier and submit compatible requests. Built-in Chat and API requests share the same active model and core admission machinery.

The user requested Bionic-like behaviour, clarified that the existing configuration page needs connecting, then explicitly authorized Task 0 review, configuration/shared generation and API implementation on `feat/local-api`. ADR-0006 was explicitly accepted on 2026-10-13. This authorization does not include publication, new inference benchmarks or production deployment. Computer Use permission was restored after withdrawal; initialization failed twice before app input. D04/D07 remain open overall; implementation and fixture evidence do not establish release acceptance.

Authoritative constraints: [PRODUCT-SPEC](PRODUCT-SPEC.md) P4/P6/P8/P9, [TECHNICAL-SPEC](TECHNICAL-SPEC.md) T01-T06/T20-T24, [INTEGRATION-SPEC](INTEGRATION-SPEC.md) sections 3 and 6-7, [SECURITY-SPEC](SECURITY-SPEC.md) S08-S14/S17, [UI-SPEC](UI-SPEC.md) U19-U22, [TESTING-SPEC](TESTING-SPEC.md), [ADR-0003](decisions/0003-lm-studio-behavior-reference.md) and [ADR-0005](decisions/0005-local-generation-development.md). Existing requirements prevail over this proposal.

### Proposed delivery scope

First candidate: Windows development, loopback, one active model, required key, model listing and text chat with both response modes. This is a staged scope recommendation for review, not a newly accepted restriction on P4's eventual network API.

Retain the Network control in its existing position. Until protected network exposure is approved and implemented, it remains unavailable with an explanation. Do not enable a control that binds all interfaces without an approved contract.

Responses, legacy completions, embeddings, images/audio, tools/function calling, MCP, Anthropic compatibility, native LM Studio endpoints, model download/load/unload APIs, JIT/TTL and API-driven placement are outside this initial candidate. Reject their routes or fields explicitly. Adding them needs a separately specified capability and runtime evidence. No claim of drop-in compatibility with every LM Studio client is permitted; a client requiring Responses or tools will not work with this candidate.

## 3. Ownership and data flow

The GUI-independent core owns the public listener, public API-key policy, request validation, admission and cancellation. Electron main exposes dedicated management operations through the existing sender/frame-validated boundary. The renderer receives status and bounded non-sensitive events. Key reveal/copy is a separate explicit local operation, not a general secret-read method.

Public HTTP requests are translated to typed, caller-bound core operations. Never proxy arbitrary URLs, headers, native routes or native options. The private engine listener, its credential, slot identifiers, process handles and filesystem paths remain inaccessible. Public keys and runtime keys are distinct; possession of a public key confers no worker, Cluster, signing, storage-management or engine-control authority.

The generation service now captures immutable settings for Chat and stateless API requests. Its owned transport applies closed sampler fields and passes matching final messages/settings to token counting and generation. API requests share the admission object without creating conversations or attempts. The profile ceiling remains 512 output tokens. The loopback listener and actual-usage mapping are implemented; neither bypasses native settlement.

The existing configuration page now opens for the verified imported model and saves through the core-owned configuration database. Successful Save follows commit acknowledgement; failed Save retains the draft. Demo settings remain session-only. There is no second configuration screen or layout redesign. Advanced preferences and unevidenced load tuples remain unavailable as live options.

### 3.1 Existing configuration and proposed precedence

Core owns schema-1 configuration records keyed by verified GGUF digest, with separate load and generation groups and captured revisions. The fixed protected configuration database also retains first import times and DPAPI-protected public-key bytes. History schema 5 adds nullable captured settings; exact earlier schemas migrate atomically and legacy settings remain unknown. ADR-0006 governs these boundaries, with independent review still outstanding.

Precedence for a supported generation field is: explicit validated API override, otherwise the committed model setting. A new model record derives its effective settings from the recorded native profile, never preview values. An API override belongs to one request and never saves a default or changes another Chat/API request. The 2026-10-13 Bionic checkbox trace corrects the earlier inheritance proposal: disabled Top P means 1, Min P means 0, repeat penalty means 1, presence penalty means 0, and Seed means random selection. Manual values remain stored. The pinned native sampler represents random seed selection with unsigned 32-bit maximum, not zero. Disabled response length uses the finite approved profile budget. Initial enabled states preserve the actual profile behaviour, including a fixed seed when the profile uses one.

At admission capture model/deployment/session identity, active load revision, committed generation revision and resolved immutable request settings. A later Save, model switch or key rotation cannot rewrite the captured request. Revalidate ownership/readiness at native start. The initial live development resource evidence supports four slots and the existing configuration only; other load tuples or sampler/template mappings need their own approved capability/resource evidence. Requested unsupported settings fail with an explanation rather than being ignored or silently clamped.

The proposed maximum-response-length setting is a default, not an implicit security quota. An explicit API `max_tokens` can replace it within the approved profile ceiling and remaining context. If the optional editor limit is disabled, resolve the profile's documented default output budget. Every admitted request still needs a finite approved budget; the remaining context is not permission for an unbounded request.

## 4. HTTP compatibility contract

All details in this section are proposed initial contract values. Return JSON UTF-8 for JSON responses. No credentials in URLs, query parameters, examples, errors or logs. Authenticate even model-listing requests. Reject duplicate/ambiguous authorization, duplicate JSON object keys, invalid framing and unsupported content encodings before execution. Parser rejection must never forward work to the engine.

### 4.1 Model identity and listing

`GET /v1/models` returns HTTP 200 with `object: "list"` and a `data` array. Each entry has `id`, `object: "model"`, `created` and `owned_by: "modelloom"`. `created` is the recorded import timestamp in Unix seconds, not a fabricated model-training date.

Return one entry only while the active model is ready to accept work, including while serving admitted requests. Return an empty array when no model is callable. Use an opaque stable API identifier derived from the protected imported-model record, not a path or the native private alias. Re-import identity rules must follow the existing import contract. Copy/snippets display this exact identifier.

At admission, capture the active deployment/session/model identity. Revalidate it before native start. A request cannot be redirected to a later loaded model. With no model loaded, generation uses the observed HTTP 400 envelope described in section 4.5. Unknown identifiers while a model is callable and known-but-unavailable switching states retain the proposed `model_not_found`/`model_not_ready` rules; those branches have not been verified against Bionic. Requests cannot load, switch or modify placement.

### 4.2 Text Chat Completions request

`POST /v1/chat/completions` accepts an object with the following fields. Unknown fields are rejected with `unsupported_parameter`; never silently discard settings requested by a client.

Proposed aggregate content bound: 12,000 UTF-16 code units across all messages. This adapts the existing composer limit to an API request and requires review; it is not an existing API capability. Also enforce the 256 KiB encoded-body limit. Reject excess with an explicit size/context error; never truncate messages. Token preflight uses the same actual template, requested output reservation and context rules as generation.

The intended first profile connects the existing generation controls instead of permanently rejecting sampler fields. Proposed public mappings are `temperature`, `top_p`, `top_k`, `min_p`, `repeat_penalty`, `presence_penalty`, `seed` and `stop`, plus `max_tokens`. Enabled/disabled editor state and omitted API fields follow section 3.1. Temperature 0-2, probabilities 0-1, non-negative integer Top K, non-negative repeat penalty, presence penalty -2 to 2 and unsigned 32-bit seed are existing editor ranges to review, not evidence that every runtime accepts those values. `stop` accepts a non-empty string or non-empty array of non-empty strings within approved framing/profile limits. Finite numbers, exact types, bounds and native support must be validated in the core, not inferred from renderer validation.

The final decoder and capability table must pin each range, optional-state meaning, stop/string limits and native parameter/template mapping before the affected field is enabled. Unsupported fields or values return an explicit error. Do not claim sampler parity solely from Bionic accepting the temperature/seed probes, and do not pass arbitrary JSON fields to the native listener. The current 512-token ceiling remains a resource-profile limit; the adapter accepts smaller captured budgets.

Never accept `id_slot`, private aliases, paths, engine addresses, raw argument strings, `draft_model`, JIT `ttl` or runtime configuration. System text uses the verified model chat template; it is not permission to execute instructions or change application policy.

### 4.3 Non-streaming response

Successful requests return HTTP 200 with `id`, `object: "chat.completion"`, `created`, `model`, `choices` and `usage`. The completion identifier is opaque and unique within the deployment; `created` is the request's creation time in Unix seconds. `model` is the captured public identifier.

There is exactly one choice with `index: 0`, `message.role: "assistant"`, `message.content` containing answer text and `finish_reason` of `stop` or `length`. Thinking stays separate in the non-standard `message.reasoning_content` extension when the captured runtime supplies it. No synthetic reasoning, parsing guesses, or thinking text appended to answer content. This extension follows the documented DeepSeek-style direction; LM Studio's documented gpt-oss `reasoning` field differs (R9). Do not claim uniform reasoning-field parity.

`usage` reports integer `prompt_tokens`, `completion_tokens` and their sum as `total_tokens` from the captured template/tokenizer and runtime result. Completion usage includes emitted thinking tokens where the runtime counts them. Include `completion_tokens_details.reasoning_tokens` when the selected runtime provides trustworthy separate accounting, matching the observed Bionic field; omit an unavailable breakdown rather than inventing zero. Empty answer content is valid when the configured budget is exhausted during thinking and the outcome is `length`. No character-count approximation. If trustworthy required usage cannot be obtained for a supported configuration, that configuration cannot claim this profile; fail explicitly rather than fabricate zero. The exact runtime mapping is an implementation prerequisite.

### 4.4 Streaming response

After authentication, validation and admission, streaming returns HTTP 200 and `text/event-stream`. Each `data:` record contains a JSON `chat.completion.chunk` with stable `id`, `created` and `model`. The first choice delta identifies role `assistant`; subsequent deltas carry `content` or the separate `reasoning_content` extension. Choice index remains zero; intermediate `finish_reason` is null.

Normal completion emits the terminal choice with `finish_reason: "stop"` or `"length"` only after the shared core confirms its successful terminal outcome and required native settlement. When `include_usage` is true, emit a final usage chunk with empty `choices` and actual usage before `data: [DONE]`. Non-final usage is null or absent. `[DONE]` is a success terminator, never proof of native cancellation or slot release.

Once headers have been sent, HTTP status cannot change. Public Server Stop closes the affected connections without promising a final SSE error event, terminal choice, usage chunk or `[DONE]`, matching the observed Bionic interruption. Client disconnect may likewise receive no final event. Internal cancellation and native settlement still complete independently of socket closure. Other runtime/key-replacement failures use the proposed bounded error event in section 4.5 when the connection can still deliver it, then close without a successful terminal choice or `[DONE]`; those Bionic cases remain unverified. Clients must treat an interrupted stream as incomplete. Confirm exact behaviour with pinned SDK versions rather than advertising that every client interprets partial errors identically.

Use bounded output buffering and transport backpressure. A client that does not read cannot accumulate unbounded output or hold capacity indefinitely; reaching the approved bound cancels that caller's request and uses normal settlement. No automatic HTTP retry or stream resumption. A client retry is a new request and can duplicate generation; no idempotency guarantee is advertised.

### 4.5 Error contract

The general proposed JSON envelope is `{ "error": { "message": "<safe explanation>", "type": "<category>", "param": null, "code": "<stable code>" } }`. `param` may instead name a public invalid field. The following observed compatibility exceptions are explicit: malformed JSON returns HTTP 400 with `type: invalid_request`, `code: invalid_json`, and no required `param`; missing/unsupported POST JSON media type returns HTTP 415 with `type: invalid_request_error`, `code: unsupported_media_type`; generation with no loaded model returns HTTP 400 with `type: invalid_request_error`, `param: model` and `code: null`. The unloaded-model message should direct a ModelLoom user to Cluster, not to Bionic's CLI. Authentication precedes sensitive model-state disclosure. Other table entries remain ModelLoom proposals. Messages exclude prompts, credentials, native responses, paths and stack traces. No raw engine error passthrough.

| Status before streaming | Code/category                                                                                       | Required outcome                                                                             |
| ----------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 400                     | `invalid_request`, `unsupported_parameter`, `context_exceeded` / `invalid_request_error`            | Explain the public field or supported bound; no inference.                                   |
| 401                     | `invalid_api_key` / `authentication_error`                                                          | Same safe response for missing, invalid or revoked credentials; no model metadata.           |
| 403                     | `origin_not_allowed`, `host_not_allowed` / `permission_error`                                       | Deny browser/rebinding request; no inference.                                                |
| 404                     | `model_not_found`, `route_not_supported` / `invalid_request_error`                                  | No fallback model or route proxy.                                                            |
| 405                     | `method_not_allowed` / `invalid_request_error`                                                      | Include the supported method for a known route.                                              |
| 413 / 415               | `request_too_large` / `unsupported_media_type`                                                      | Stop reading according to bounded parser policy; no inference.                               |
| 429                     | `queue_full`, `rate_limited` / `rate_limit_error`                                                   | Bounded immediate rejection; no hidden engine queue or invented retry estimate.              |
| 503                     | `model_not_ready`, `server_stopping`, `runtime_unavailable`, `storage_unavailable` / `server_error` | No implicit load/restart/replay; storage failure remains fail-closed for shared core safety. |
| 504                     | `queue_timeout`, `generation_timeout` / `server_error`                                              | Cancel only the associated request and retain capacity until settlement.                     |
| 500                     | `internal_error` / `server_error`                                                                   | Sanitized failure; record bounded diagnostics.                                               |

HTTP syntax errors may be rejected by the HTTP implementation before JSON framing is possible. Oversized headers produce a bounded 431 response or connection close. Parser errors cannot be represented as successful application replies.

Server Stop follows the connection-close rule in section 4.4 and does not require an error event. For a deliverable stream interrupted by key replacement or runtime failure, propose `request_cancelled` or `runtime_unavailable` in the error envelope. Client disconnect is cancellation, not a successful completed result. No public cancel-by-guessed-ID endpoint is added.

## 5. Shared scheduling and request lifecycle

Reuse one core queue for Chat and API. The proposed initial development profile retains ADR-0005's four active, eight pending, FIFO admission, 120-second pending wait, 300-second generation deadline and five-second native-cancellation confirmation. These are inherited development bounds, not measured LM Studio limits, distributed capacity or release acceptance.

Bionic's observed decode cancellation sent a native cancel and released the slot. Its log warns that prompt processing may finish before cancellation takes effect; no long-prefill bound was measured. The five-second value is a proposed ModelLoom confirmation/recovery deadline, not a promise of Bionic prefill responsiveness. G5 must review prefill/decode cancellation, continued capacity reservation and escalation isolation. A timeout cannot mint a free slot or silently kill unrelated Chat work to satisfy a public-server Stop claim; if reviewed recovery requires stopping the shared runtime, report that broader interruption explicitly.

Admission captures caller authority and model/session identity. Disconnect, timeout, key replacement and API Stop cancel only the affected API work. Queued work is removed without entering the engine. Active capacity is returned only after the existing authenticated native settlement contract confirms it. An aborted HTTP stream or parser EOF is insufficient. Unconfirmed cancellation closes affected admission and uses reviewed owned cleanup; never mint replacement capacity.

Chat remains usable when the public API server is stopped, unless shared runtime/storage failure genuinely prevents it. A public client cannot stop Chat requests. Full app Quit and explicit model switching use the existing shared lifecycle, cancel/resolve all affected work and prevent replay on restart. An independent headless deployment retains its own lifecycle.

Global FIFO and saturation rejection do not establish per-client fairness. With one public key, client processes cannot be reliably distinguished by bearer authority, IP or a caller-supplied label. D09 must review starvation/abuse and mixed Chat/API load before extending limits or claiming fair allocation. Admission does not silently reduce context, change quantization or alter sampling to accept more work.

## 6. Server and credential management

### 6.1 Server lifecycle and address

Proposed states: stopped, starting, running, stopping and failed. Start validates the host's development capability, key availability, exposure policy and requested bind before opening a socket. Start can succeed without a model; listing is empty and generation fails until the user loads one in Cluster. Running means the listener exists, not that inference is ready.

Keep configured port/interface separate from actual listening address/port. The active endpoint is unavailable outside running; successful bind captures the socket's actual address. Never display a configured value as evidence that startup succeeded. The shipped Bionic provider serializes listener transitions and restarts a running server when port/interface/CORS changes. Proposed ModelLoom settings changes use the same ordered stop/restart pattern after reviewed management validation, interrupt only that listener's API work, and retain configured versus actual state on failure. This restart path has static Bionic evidence only; startup, failure and connection-teardown behaviour still need live ModelLoom tests. It does not authorize CORS or network exposure.

Propose port 1234 as the initial reference-aligned configured value, with explicit configuration before start. LM Studio documentation uses 1234 in examples; that alone is not proof of every installed default. ModelLoom's existing 8000 display is an example, not a required port. Changing the displayed actual endpoint is data binding within the existing layout, not permission to add a settings panel. Exact configuration access needs the management-contract review.

Bind only `127.0.0.1` initially; IPv6 is unavailable until an explicit `::1` contract/test is added. Never bind wildcard as a fallback. Port conflicts fail visibly without changing the port, stopping another program or exposing a different interface. Endpoint copy/snippets reflect the actual bound address. Stop closes new admission/listening, cancels queued/active API work, joins settlement and reports completion only when the listener/connections are closed. It does not unload a model merely because API serving stopped.

No auto-start on installation/app launch or silent restart after failure in the first candidate. Stored non-secret settings cannot create a listener without the explicit Start action. Minimize leaves a deliberately started server running; window X performs full Quit. Future independent headless API serving needs its own reviewed lifecycle and platform evidence.

### 6.2 Public key proposal

Use one active public API key per deployment in the first candidate, matching the existing masked field and Generate/Regenerate controls. This differs from LM Studio's named multi-token/permission management; do not add a token-management screen under this task. Authority is limited to the supported inference/model-listing operations.

Generate at least 256 bits of randomness using the platform CSPRNG and standard encoding; use established secret verification facilities, not custom cryptography. Bearer authorization is the only credential input. Keep the key distinct from internal runtime, signing and networking secrets.

The existing explicit reveal/copy controls require recoverable secret storage, unlike LM Studio's creation-only display. Propose a Windows OS-protected secret store with restricted managed paths and no plaintext fallback. Exact adapter, retained file identities, migration, locked-store handling, comparison and transient IPC lifetime require focused security review before implementation. Existing development signing custody is not automatically authority to reuse its secret-handling path for API keys.

Core/main owns the credential. Renderer status is masked and never contains the secret. Explicit reveal may deliver only the requested key to short-lived presentation, masked again on blur/navigation or after 30 seconds; never persist it in renderer stores, logs or analytics. Copy writes the key only after the explicit action, without clipboard reads or a promise that other applications cannot read the clipboard. Exact clipboard/IPC handling needs review. Failure to protect/read the key blocks API Start, without preventing unrelated history viewing.

Regenerate must explain that clients need the replacement and existing API work will be cancelled. Commit the new protected key generation and invalidate the old authority atomically. Recheck authority at admission and native start. Invalidate established keep-alive authentication and cancel all queued/active API work under the old generation, awaiting normal settlement. A failed replacement keeps the old key valid and reports failure; no partially active key pair. Stop retains the key; key removal/revocation disables API access and stops its requests. These in-flight semantics are proposals, not documented LM Studio observations.

## 7. Exposure and browser policy

Loopback HTTP is the first candidate transport. It is not protection against a compromised OS or same-user account. Bind and Host validation must use parsed exact authorities for the configured listener, not suffix matching. Proposed Host allowlist: `127.0.0.1:<port>` and `localhost:<port>`, with normal case normalization and explicit-port validation. A local process is still required to authenticate.

No browser clients initially: reject any request carrying an Origin header, including `null`; emit no permissive CORS response. Unauthenticated preflight cannot run inference or disclose model data. Test browser-shaped simple requests, preflight, DNS rebinding and crafted Host headers independently of bearer validation. Future browser support needs explicit origin and preflight rules, not a wildcard switch copied from the reference.

Eventual Network mode must select permitted interfaces explicitly, publish actual addresses, keep required keys and protect transport confidentiality/authenticity. Plain LAN bearer HTTP, automatic `0.0.0.0`, public forwarding, automatic firewall changes and tailnet membership as authorization are not accepted. TLS certificate/trust management or a reviewed private transport must be specified before enablement. Existing Tailscale installation does not complete this work, and API permission never grants worker participation.

Settings -> Network remains the existing home for cluster/private-network configuration. No redesign, new network wizard or policy-setting surface is authorized by this specification. D02/D03 remain open for affected private-network integration; D07 retains API exposure responsibility.

## 8. Storage, metrics and existing UI

The user's current UI reference is ChatGPT across the whole app, continuing the existing direction. Use the installed apple-design skill for future interaction/motion/polish work, preserving the existing ModelLoom composition, controls, accessibility, typography tokens and layering requirements until a separately reviewed UI change. This configuration/API integration connects existing screens; it does not add a duplicate model-settings surface or adopt Bionic's agent workspace, tool permissions or account screens.

Proposed Chat Completions are stateless: each request supplies its conversation. API prompts, thinking and answers do not create built-in Chat history, and no public route reads existing conversations. Request IDs do not grant history access. Temporary execution buffers remain bounded and are released after terminal settlement. This is a proposed privacy boundary, not a claim that LM Studio's GUI history was observed.

Preserve the approved stacked Server, Access, Integration and Server logs layout. Enable each existing control only when its capability is implemented and verified. Unavailable Network and unsupported API features remain explained; no fake key, model, address, metrics or logs. Key actions use the narrow local management boundary, not the public inference API.

Proposed metrics for the existing labels:

- Uptime: monotonic elapsed time since this listener successfully bound; reset on a new server instance.
- Requests: authenticated Chat Completions admitted by this listener instance, including later failed/cancelled work; excludes listing, parser/auth failures and built-in Chat.
- Response time: rolling mean of total elapsed time from admission to normal completion for the last 100 completed API requests, including queue wait and generation. Include both streaming modes; exclude interrupted requests. No samples means unavailable. Explain the definition through existing caption/accessible help, without adding a panel.

Do not label this response time as network RTT or time to first token. Logs contain bounded timestamps, lifecycle/request IDs, safe event categories/status and durations, without headers, keys, prompts, messages, outputs, query strings or raw engine errors. Proposed viewer retention: last 500 records and at most 256 KiB, evict oldest records first; Clear removes only viewer records, not history or audit evidence elsewhere. No persistent content logging or telemetry is added. Diagnostic exports use the existing redaction requirements.

Integration snippets use the actual endpoint, served public model ID, declared supported fields and an environment-variable/placeholder key. Text-only copy never inserts the real key into an exported example. Exact Python/JavaScript/OpenAI SDK versions and streaming error behaviour must be tested before advertising interoperability. Examples cannot execute or trigger model loading from the renderer.
