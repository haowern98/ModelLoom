# Automatic Windows sharing setup

Goal: enabling Allow connections prepares GPU helpers, binds the selected private address, installs a narrow owned Windows Firewall rule, and advertises readiness only after successful setup.

Authorization: the user approved the described firewall lifecycle and the exact adjacent loading spinner with PROCEED on 2026-10-23. Work remains in the existing checkout; preserve all previous changes and staged files. The subsequent user request authorizes sensible local commits with no file-count limit. No push is requested.

Architecture: one separate network-mode instance of the verified peer helper per sharing session. The native operation accepts only the selected private IPv4 address. It derives the actual listener process from the PID-bound launcher ancestry, retains handles and creation identities, and verifies both fixed TCP listeners before and after rule creation. Its rule targets that executable, address and interface on TCP 49301 and 49302. LAN scope is LocalSubnet; the selected Tailscale interface uses its CGNAT address range. These outer firewall rules enable control-channel reachability, not native worker process isolation or peer authorization. Existing code verification, mTLS pinning and restricted worker protections remain mandatory and unchanged.

The elevated helper owns a uniquely named rule. Rule creation/readback, live owner/listener/interface/policy validation, deletion and stale-rule recovery are bounded and fail closed. Only complete matching app-owned rule records with provably dead helper identities qualify for recovery. No arbitrary executable, port, command, firewall-disable operation, or permanent service is exposed. Unexpected helper loss stops admission and owned workers. Confirmed rule removal precedes successful teardown and release of runtime seals.

Tech stack: existing TypeScript peer core and Windows C++ helper, Windows Firewall COM APIs, existing private PowerShell relay, React/CSS, Vitest.
